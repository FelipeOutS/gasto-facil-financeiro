- WhatsApp inbound authorization no longer lets the legacy canary flag block paid eligible users, because WhatsApp is released for all paid plans.
- WhatsApp quota SQL functions must qualify table columns or use `#variable_conflict use_column`, because `RETURNS TABLE` output names otherwise collide with column names in PL/pgSQL.
- WhatsApp conversation replies are logged in `whatsapp_outbound_messages` (hash/last4 only, no text) and reconciled from `whatsapp_notification_status_events` by Meta message id, because status events are the single durable callback store.
- `FEATURE_PLAN_WHITELIST.whatsapp` must mirror SQL `has_feature_access(_, 'whatsapp')`, because UI and backend gates must agree.
- WhatsApp setup CTAs use the existing `/whatsapp` route and upgrade presentations use the real feature gate, because presentation must never invent a destination or grant access.
- WhatsApp card registration (Flow or conversation) creates rows in the shared `cartoes` table via `src/server/cartao-cadastro.server.ts`, which re-checks link, `cartoes_basico` access, shared validation (`src/lib/cartao-validacao.ts`, also used by the site form), name duplicity and a deterministic id per request, because the service-role client bypasses RLS.
- GI Agenda: `agenda_items` is the single source for reminders/appointments; site (`src/lib/agenda.functions.ts`) and WhatsApp (`src/server/whatsapp-agenda.server.ts`) both go through `src/server/agenda.server.ts`, because the two channels must always show the same data.
- Agenda financial reminders store only (source_type, source_id, days before) and read amount/due date live at send time, because financial modules own those values.
- Agenda alerts reuse `whatsapp_notifications` (entity_type `agenda_item`); every change cancels pending rows and re-enqueues, and the dispatcher revalidates before sending, because there must be one notification queue.
- Every read of `gastos` must filter `.is("deleted_at", null)` or carry a `soft-delete-exceção:` comment, enforced by tests/whatsapp-gastos-soft-delete-f3.test.ts, because soft-deleted expenses must never be shown or summed.
- Shopping assistant lives in src/server/shopping/ as pure, dependency-injected modules (not wired to the WhatsApp pipeline yet); quota counts real API calls, not messages, because the legacy whatsapp_claim_research RPC counts rows.
- Shopping assistant routes through `src/server/shopping/whatsapp-shopping.server.ts` behind `WHATSAPP_SHOPPING_ENABLED` (off by default) and uses only the DB quota RPCs (`whatsapp_shopping_reserve/finish`); the in-memory store is test-only, because quota must be shared across workers and fail closed when the SQL is absent.
- Shopping presentation uses a structured capacity summary and deferred per-offer links from the existing user+phone context; link/store replies skip financial reads and quota, because display-only follow-ups must not trigger research or expose another conversation.
- Site extrato reversal goes only through RPC `reverter_extrato_atomic` (no client-side DELETE fallback; fails closed if the RPC is missing), because multi-table deletes must be all-or-nothing and keep user-edited rows.
- WhatsApp editing and single-entry deletion/restoration of existing gastos/receitas go through `src/server/whatsapp-editar-antigo.server.ts` (`acao` editar|excluir|restaurar): per-step state in `whatsapp_messages.parsed` (kind `wa_edit_old`, fresh nonce per step) and a conditional UPDATE on `updated_at`; deletion/restoration use service-only `whatsapp_entry_mutate_v2` after explicit schema rollout, preserving F2 markers, CAS and an immutable mutation journal on the same row (never physical DELETE or a replacement row); both and blocks parcelado/recorrente/bem/crédito/extrato/conta-a-pagar entries, because stale buttons, replays and concurrent site edits must never overwrite, reapply or break financial links.
- WhatsApp month-wide delete/restore lives in `src/server/whatsapp-lote-mes.server.ts`, locked by `LOTE_MES_RELEASE_AUTHORIZED` and executed only via RPCs `wa_lote_mes_excluir/restaurar` (candidate `docs/migrations-candidate/whatsapp-lote-mes.sql`, service_role only), with restore limited to the batch's own IDs and deleted_at stamp, because bulk changes must be all-or-nothing and never revive unrelated deletions.
- WhatsApp card-listing intent is recognized only by `isListarCartoesIntent` (src/server/whatsapp-listar-cartoes.ts, closed word list, no digits/action verbs), because broad regexes would capture card registration, invoice or payment requests.
- Subdirectories may have their own AGENTS.md (e.g. src/server/pluggy/) — read it before changing files there.
- WhatsApp financial reorganization uses injected orchestration with no production writer while unauthorized; candidate apply/restore require operation-bound expiring codes, owner snapshots and F2 markers. Candidate offline generation guards serialize with reset and check effective identity before privileged marker bypass; queue versions are immutable. Opening balances remain a separate unreleased account baseline, never income; linked modules stay blocked until their accounting contract is implemented.
- Reorganization card accounting permits only unpaid single purchases with explicit invoice competence, snapshots cards/invoices and never rewrites settlement rows; paid/partial/ambiguous scopes remain blocked because no cash settlement ledger exists.
- Account baseline reads are separate from monthly income/expense/reserve totals and shown only for the authenticated owner; a bank-level end-of-day baseline is not a calculated current bank balance because movements lack canonical bank attribution.
- Candidate universal fencing quarantines unversioned legacy expense/income writers after reset, including service-role writes; generation hydration never re-labels queued operations, and broader writer migration remains required before release.

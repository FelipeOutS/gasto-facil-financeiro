# Pluggy rules (read before changing Pluggy code)
- Pluggy (`src/lib/pluggy/rules.ts`, `src/server/pluggy/*`): two-UUID allowlist AND `owner`, Sandbox-only unless `PLUGGY_LIVE_READONLY_AUTHORIZED` (then only allowlisted real institutions, staging only; imports stay Sandbox-only in SQL), writes only `pluggy_*` (candidate SQL tested by `scripts/test-pluggy-sql.sh`); the webhook only enqueues and `/api/public/pluggy/worker` processes via claim/lease RPCs with limited retries, because test data must never reach real finances and acks must be durable and idempotent.
- Pluggy → Gastos/Receitas import uses the pure planner and candidate transactional RPCs (`pluggy_import_apply`/`pluggy_import_revert`, service_role only), gated both by `PLUGGY_IMPORT_RELEASE_AUTHORIZED` and an unconditional SQL `pluggy_assert_financial_release` rejection; only isolated SQL tests replace that gate, because direct service calls must not authorize shared financial writes.
- The import UI calls authenticated `src/lib/pluggy/import.functions.ts`; `pluggy-import-store.server.ts` reads through the caller's RLS client and loads privileged RPC writers only after the release gate, because browser-supplied user IDs, plans and release overrides must never authorize financial writes.
- Successful staging sync and transaction-deletion staging call the gated incremental hook before acknowledging processing; import reversal undoes only rows created by that batch, not incremental mutations, because source-key idempotency supports retries while update rollback requires a separately approved journal.
- Card-link simulation is a pure owner-validated preview and never a writer input; corrections/unlinks serialize with imports, deactivate rather than delete links and send previously related purchases to review without moving their card or invoice, because changing an association must not rewrite financial history.
- Candidate new-table FKs and relationship triggers validate transaction, owner, card, target origin and batch without changing existing financial tables; generic F4 rejects persisted Pluggy batch/row origins before replay or deletion, because browser metadata is not authority.
- Webhooks authenticate only by header and require provider event IDs for accepted events; connect tokens omit callback URLs, because secrets must not enter URLs and external webhook registration needs separate authorization.
- Real Mercado Pago (606) preview/first import live in `src/lib/pluggy/real-preview.ts` + `real-import.functions.ts` (Felipe+owner only); writes only through candidate SQL `pluggy_import_apply_real_once`/`pluggy_import_revert_real_once`, gated by code flag `PLUGGY_REAL_FIRST_IMPORT_AUTHORIZED` and a literal one-shot row in `pluggy_real_import_grants` whose batch_id is fixed at approval (server reads it; the browser never supplies a batch) and whose SQL exception matches the exact user/account/transaction/table/batch, because the global `pluggy_assert_financial_release()` lock must stay intact for every other path.
